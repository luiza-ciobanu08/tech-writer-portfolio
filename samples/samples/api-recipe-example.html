Process Sales Invoices

In Banqup, any uploaded file undergoes a process where invoice data is extracted and checked for sanity and accuracy. After a successful validation process, the document is sent automatically to the customer. After that, you can view details about the document and update the payment status.

For more information on how the sales invoice flow works in Banqup, check out the Glossary and the sales invoice flow.

Prerequisites​

  • The invoice is a valid UBL, XML, or PDF.
  • You have Banqup permissions.
  • The resource IDs necessary to perform the API calls are:
    • spaceId
    • connectionId
Duplicate prevention & idempotency

Banqup uses a combination of the filename and request metadata to help identify duplicate uploads. To safely handle network timeouts or retries without issuing duplicate invoices, your integration should always log and map your internal system's invoice tracking IDs to Banqup's returned file id (from Step 1) before executing automated retries.

Step 1: Create file​

Endpoint: POST /documents/core/transaction/v1/spaces/{spaceId}/files

Path parameter: spaceId

curl -L 'https://{{serverURL}}/documents/core/transaction/v1/spaces/{spaceId}/files' \
-H 'Content-Type: application/json' \
-H 'Accept: application/json' \
-H 'Authorization: Bearer YOUR_TOKEN' \
-d '{
    "filename": "S_BE0479909676_999",
    "description": "xml upload for document ABC2025-10-29",
    "creatorSubject": "00000001-0001-0001-0001-000000000000",
    "creatorType": "user",
    "retentionTime": "2029-09-30T08:30:08.424Z",
    "fileSize": 57308,
    "fileType": "xml",
    "contentType": "application/xml",
    "source": "com.unifiedpost.btx.connectors:peppol",
    "tags": ["tag1", "tag2"],
    "metadata": {
        "folder": "SALES",
        "documentCategory": "INVOICE"
    }
}'

Successful response: Save the id returned in the response — you will use it as fileId in the following steps.

{
    "id": "a751dea0-cb12-4cde-8734-c6d839c863c3",
    "filename": "S_BE0479909676_999",
    "status": "AWAITING_UPLOAD",
    "fileSize": 57308,
    "fileType": "application/xml",
    "contentType": "application/xml",
    "uploadUrl": "https://storage.googleapis.com/...",
    "metadata": {
        "folder": "SALES",
        "documentCategory": "INVOICE"
    },
    "createdAt": "2025-10-29T08:09:44.020545597Z",
    "updatedAt": "2025-10-29T08:09:44.020545597Z"
}

Step 2: Upload file​

Endpoint: PUT /{uploadUrl} — returned in the Step 1 response.

The uploadUrl is a presigned GCP URL that allows temporary, secure access to upload the file to a storage bucket.

Request body: Attach the file in PDF, UBL, or XML format. Content type: binary.

Upload requirement

The Content-Type header must exactly match the contentType value specified in the Step 1 request body (e.g., application/xml). A mismatch will result in a 403 Forbidden or 400 Bad Request error.

Successful response: The file has been accepted for processing. To check the file status, see Step 3.1.

Document processing and delivery​

If the document is processed successfully, the invoice is sent automatically to the customer. No action is required at this stage.

Step 3: View results​

  • Document
  • Document events
  • Customer

Step 3.1: Check file status​

Every newly created file undergoes validation by Banqup, reflected in different file statuses. Use this endpoint to check the file status.

Endpoint: GET /documents/core/transaction/v1/spaces/{spaceId}/files/{fileId}

Path parameters:

  • spaceId
  • fileId
curl -L 'https://{{serverURL}}/documents/core/transaction/v1/spaces/{spaceId}/files/{fileId}' \
-H 'Accept: application/json' \
-H 'Authorization: Bearer YOUR_TOKEN'

Successful response:

Step 3.2: Retrieve the document ID​

Endpoint: GET /documents/core/transaction/v1/spaces/{spaceId}/files/{fileId}/documents

Path parameters:

  • spaceId
  • fileId
curl -L 'https://{{serverURL}}/documents/core/transaction/v1/spaces/{spaceId}/files/{fileId}/documents' \
-H 'Accept: application/json' \
-H 'Authorization: Bearer YOUR_TOKEN'

Successful response: Save the id returned — you will use it as documentId in Step 4.

{
    "documents": [
        {
            "id": "53705523-fd58-4510-86f8-b7619a75a4b9"
        }
    ]
}

Step 3.3: Retrieve document results​

Endpoint: GET /documents/core/transaction/v2/spaces/{spaceId}/documents/{documentId}

Path parameters:

  • spaceId
  • documentId

Query parameters (optional):

  • include: processingData, validationData, connections, lines
curl -L 'https://{{serverURL}}/documents/core/transaction/v2/spaces/{spaceId}/documents/{documentId}' \
-H 'Accept: application/json' \
-H 'Authorization: Bearer YOUR_TOKEN'
Validation failures

If "validated": false is returned in the response payload, check the spaceExtensions object under validationData.

Common rejection reasons:

  • peppol validation failure: The UBL/XML violates Peppol standard specifications, for example a missing mandatory tax schema.
  • dataExtraction mismatch: Computed line item totals do not match the grossAmount or payableAmount in the document totals.

If an automatically processed invoice fails validation, it will not be delivered to the customer. You will need to upload a corrected document.

Step 4: Update payment status​

In this example, the document is marked as paid.

Endpoint: POST /payments/reconciliation/documents/v1/spaces/{spaceId}/documents/{documentId}:markAsPaid

Path parameters:

  • spaceId
  • documentId — retrieved in Step 3.2
curl -L 'https://{{serverURL}}/payments/reconciliation/documents/v1/spaces/{spaceId}/documents/{documentId}:markAsPaid' \
-H 'Content-Type: application/json' \
-d '{
    "comment": "Payment received for Invoice ABC2025-10-29",
    "paymentAmount": "20",
    "paymentDate": "2026-01-15",
    "paymentReferenceNumber": "GHT1234",
    "paymentMethod": "BANK_TRANSFER",
    "sharePaymentStatus": true
}'

Successful response: 200 OK

Check the response body for processing failures

The :markAsPaid endpoint returns 200 OK even if some documents failed to update. Your integration must inspect the response body to confirm that your document IDs are not listed in the failure array.

Common reasons for failure:

  • The documentId does not exist or has been deleted.
  • The document is in an invalid state, for example still PROCESSING.
